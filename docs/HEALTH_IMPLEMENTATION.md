# v0.2.0 整机健康监测修正

> 版本说明：本文保留对应旧版设计/验证范围。v0.4.0已改为机器人经网线上位机relay上传，当前启动参数、凭据位置和退出行为以 [WIRED_RELAY.md](WIRED_RELAY.md) 为准；旧测试记录不构成新拓扑验收。

本轮纠正的目标：现场使用原生上位机，首页直接看电池、温度、故障和主机负载；后台持续采集、入库并向大屏汇总。关节曲线是详细分析工具，不再代替整机健康总览。

**当前没有实机SSH条件。本版完成软件适配、健康数据链路和页面验证，未完成实机接通；电机温度只完成契约与展示，运控发布接口仍未实现。** 所有预览中生成的电池/温度均明确标记模拟，不是机器人实测。

## 真实来源与当前完成状态

| 指标 | 已实现读取方式 | 当前边界 |
|---|---|---|
| 电池SoC、电压、电流、供电开关 | 默认跟随bms.service新journal；支持普通BMS、GFCAN和NRF格式 | 日志不含逐字段采样时间，旧协议可能保留上轮字段 |
| 电池温度、保护位 | 显式指定已运行rp-server地址，仅GET /api/status | 缓存快照无字段采样时间/valid位；0°C初始化歧义显示未知；不采可能为占位0的SoH |
| 主机温度 | 机器人侧读取每个thermal_zone的type/temp，毫摄氏度转°C | 保留热区编号与内核名称，不猜CPU/GPU/NPU映射；不冒充电机/电池温度 |
| CPU/内存使用率 | /proc/stat差值、/proc/meminfo MemAvailable | CPU首次仅建基线，不造0；无可用数据则未知 |
| 已上报电机故障 | 可选rp-server GET的motor_errors | 非零原始驱动ID/故障码，不猜对应ROS关节；空列表不能证明无故障 |
| 各电机/MOS温度与完整故障覆盖 | 已支持数据契约、摘要、健康页、表格和历史查询 | 当前ROS/GET未发布；还需在实际运控中输出已有驱动缓存。不能重新初始化第二个电机控制器 |

生产者源码、固定commit、协议语义和运控最小桥接依据见 [HEALTH_SOURCES.md](HEALTH_SOURCES.md)。这次沿用户给的RP1导航仓库追踪到了现有BMS和rp-server，而非将来源核查交给用户。

## 时效与健康含义

- 运动预览1秒失效；低频健康观测5秒失效，这是当前软件时效参数，不是硬件告警阈值。
- BMS journal只接受5秒内记录，拒绝过旧/明显未来时间。4秒前的日志刚读到仍为约4秒年龄，不重新获得5秒寿命；重复/乱序日志不增加样本或刷新时间。
- rp-server成功响应只证明HTTP快照刚到达。即使值恒定，也不能凭恒定判坏或给字段刷新硬件采样时间；首页明确缓存来源，不能据此确认硬件实时健康。
- 原始保护位非零、原始电机故障码非零显示上报异常；原始位定义依实际BMS/驱动协议核对，未擅自解码。
- 缺任何当前要求的核心健康来源，综合状态为监测不完整。数据齐全时也只称观测中；没有配置温度、电压等判据，不称“整机健康通过”。
- 温度、电量0和“没有数据”不同。SoC=0%正常保留；rp-server温度0存在初始化歧义，不声称有效0°C。
- 普通BMS Power ON/OFF是电池供电开关；NRF的48V/5V电源轨分别保留并明确标识，不混成总开关。V×A仅标有符号计算功率，不猜充放电方向。
- 原始电机故障ID不等于规范ROS关节索引；缺总线身份时不做物理关联。

## 启动与接入

桌面启动不变，默认打开健康页：

```bash
rp1-monitor desktop --url http://127.0.0.1:8891
```

机器人侧ROS采集默认同时观察本机主机健康和BMS新日志；完整命令见 [ROS_CONNECT.md](ROS_CONNECT.md)。若实机**已经运行并版本匹配**的rp-server，可追加：

```text
--rp-server-url http://127.0.0.1:8765
```

此参数只读已有服务，不启动/停止服务。禁止为监控新启动rp-server，避免它初始化第二套硬件并竞争CAN。journal模式拿不到电池温度/保护位时，界面显示未提供。采集必须在机器人侧运行，不能把现场电脑自己的温度作为机器人温度。

## 验证证据与仍未完成的工作

本轮已执行日志样本/临时sysfs-proc树/Mock HTTP与隔离数据库自动验证，实际Qt窗口、健康卡失联清空、原始32位故障码显示和小窗布局检查，以及五个模拟采集进程全链路验证。具体结果与源码哈希见 health-verification.json；过程结果见 health-e2e-result.json（本机历史材料，不随源码发布），独立审查见 health-review.md（本机历史材料，不随源码发布）。

五台实际进程验证：健康值进入中央；App关闭后仍上报；后端断开时有3条待传，恢复后补传；一台离线只使其健康值失效，另外四台继续。该次用时19.15秒，83个窗口，平均JSON 32778字节/窗口。模拟全健康字段每秒存30天约79.13GiB/机器人，仅JSON，不含表/索引/WAL/备份；不是已配置30天保留策略或长时间实机容量验收。

仍未完成：实机连接、实际BMS型号/版本核对、电机健康只读发布、逐字段有效反馈时间、保护位物理语义、公司确认的温度/电压判据、运动负载下开销/延迟及长时间稳定性。没有接入这些项之前，不交付“整机健康已验收”结论。

使用karpathy-guidelines审查范围与假设，ui-ux-pro-max指导主次布局，沿用FastAPI/API/PostgreSQL相关技能检查共享契约、读写权限、入库和幂等。技能是开发指导，不是产品额外运行组件。
