## 管理功能

| 操作 | 实际行为 |
|---|---|
| 新建机器人 | 校验ID、名称、来源，生成高熵设备Key；新界面同时提交完整机型与温度配置，登记、首个配置版本及审计同事务；只返回部署文件引用，不在页面显示Key |
| 修改档案 | 修改名称与中央登记启用状态；提交旧值防止相互覆盖；停用立即拒绝后续上传 |
| 机型与关节档案 | 选择24／28自由度，维护硬件版本、实际关节名称、总线与电机编号、图上部位；关节清单必须完整，实际名称及总线内编号不重复；未知信息留空，ROS2物理映射确认前须填写全部实际关节名称 |
| 温度策略与版本 | 分别配置本机器人电机/MOS温度限值及显示色阶；不提供默认安全限值。保存必须带预期版本与原因，冲突要求刷新；每次追加不可变版本和审计，可查看历史版本 |
| 更正历史指标 | 先查询指标和时间，核对原始观测，再填写last及适用的min/max；必须保留count/age和原始单位、时间 |
| 排除与撤销 | 可标记某指标观测无效；撤销时新增restore版本，保留更正轨迹 |
| 查看操作记录 | 展示数据库个人登录、时间、原因及前后内容；审计不能由业务管理员直接修改 |

原始遥测、原始归档、原始哈希和历史告警不覆盖。更正层在管理页显式展示，大屏和诊断的原始证据继续使用原始值。这里的“启用/停用”仅管理数据接入，不启停机器人程序或电机。

创建的设备Key写入 `runtime/postgres-central/management/device-keys/` 下0600文件，供授权部署人员为上位机relay配置。机器人仍不持有中央地址或凭据。数据库模式下设备配置文件仅补充未登记ID，不覆盖名称、启用状态或已有凭据，新建设备不会被服务重启停用。

机型和温度配置通过独立的 `monitor_robot_config_versions` 追加保存。中央大屏与告警读取各机器人最新有效版本；上位机relay只能读取自身凭据绑定机器人的非秘密配置，再提供给本机界面。已有设备没有数据库版本时继续使用原JSON配置。电机/MOS规则按机器人替换，全局电池和主机温度规则保留；持久告警记录实际策略摘要与配置版本。保存新版本后，旧告警在重新评估前明确标记过期，不自动宣布恢复。色阶与安全限值不同，资料未核对的部位映射仍标记待确认。

## 数据库部署

| 项目 | 当前值 |
|---|---|
| PostgreSQL | 18.6，官方镜像固定digest，见验证JSON |
| Docker项目/容器 | `rp1-monitor-central` / `rp1-monitor-central-postgres-1` |
| 连接 | `127.0.0.1:55433`，数据库 `rp1_monitor`，schema `rp1_monitor` |
| 表 | 核心11张＋历史更正/审计2张＋机器人配置版本1张，共14张 |
| 身份 | API、个人管理员、只读查询、归档分别独立登录；迁移维护使用独立所有者 |
| 资源与数据 | 2GiB容器内存上限；专用数据目录；无旧库导入、无原始数据删除 |
| 网络 | 专用bridge，关闭IP masquerade，仅发布宿主回环端口；不接入原平台网络 |
| 已有平台 | 原有55432数据库与8088/8000服务没有被修改或重建 |

应用以非所有者身份运行并使用 `--no-initialize`。管理员登录还验证实际SESSION_USER与配置一致，拒绝超级用户、BYPASSRLS、app/archiver/executor成员、对象所有者和直接表/列写权限；每个管理账号必须绑定不同的个人数据库登录。管理函数的无登录所有者不授予业务账号。

已显式执行001、002、004、005。005不纳入核心11表自动建表流程，也不改写原始遥测；管理员仅能通过 `admin_save_robot_configuration` 与 `admin_create_robot_with_configuration` 保存配置或原子创建带首配置的机器人。函数固定安全search_path、使用完整schema名称、撤销PUBLIC执行权，以数据库SESSION_USER与时间写入 `configuration.updated` 审计。API、只读查询和归档身份只有配置读取权，业务管理员不能直接插入、更新、删除配置版本或取得内部执行角色。

实际Compose和连接文件保存在私有的 `runtime/postgres-central/`，未提交运行密码。主目录0700；PG18挂载父目录允许容器用户遍历，真正PGDATA保持0700。健康检查使用容器postgres系统身份，配合本地peer及TCP SCRAM认证。

中央容量接口已显式绑定本次数据库卷与归档目录的文件系统ID。大屏显示实际剩余空间；路径失效或设备ID变化时回到unknown，远程数据库不能使用此本机探测。两个目录当前位于同一磁盘，容量不能相加；该电脑实际卷并非5TB规划存储。默认10GiB预留仅为本次部署观察值，会显示不足提示，不代表已增加全局持久容量告警。

## 启停与维护

数据库使用 `unless-stopped` 重启策略。已有环境启动用：

```bash
docker compose -f runtime/postgres-central/compose.yml up -d
```

大屏、管理API、两台模拟采集端和relay由独立主机进程启动：

```bash
env -u PYTHONPATH -u PYTHONHOME .venv/bin/python scripts/run_central_preview.py \
  --runtime runtime/postgres-central --port 18940
```

该命令需保持运行，Ctrl+C仅停止本次创建的预览进程，数据库容器继续运行。它使用两个模拟来源，不是机器人生产启动器，不会自动安装系统服务。

创建全新环境的脚本是 `scripts/setup_central_postgres.py`；它要求新目录、空闲端口和无同名Compose项目，拒绝覆盖既有库。不要将创建脚本当作启动或升级命令。首次初始化的恢复模式仅接受相同Compose路径及配置，并要求目标schema尚不存在；不重放已经完成的迁移。
