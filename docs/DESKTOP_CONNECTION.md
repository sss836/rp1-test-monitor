# 上位机桌面读取机器人

桌面程序只订阅监控数据，不启动运控、不操作电机。机器人采集端、网线 SSH 隧道、上位机 relay 是独立后台；桌面和网页读取同一台机器人的观测。

上位机左侧新增独立 [硬件自检](HARDWARE_CHECKS.md) 页面，支持手动调用 14 项 RoboPi TUI 被动插件及各项历史。刷新不执行检查，原机器人采集端需先配置对应执行器；本机更新界面不会自动升级机器人。

## 推荐：连接上位机后台 relay

先由部署脚本启动机器人采集端、独立 SSH 隧道和本机 relay，再启动桌面。若本机 relay 监听 `18972`：

```bash
rp1-monitor desktop --url http://127.0.0.1:18972
```

在“设备设置”选择“上位机后台 relay（推荐）”，服务地址填写本机 relay 的根地址。不要填写中央网页地址、`/admin` 或机器人 IP。产品原有默认地址仍为 `http://127.0.0.1:8892`，实际端口由部署配置决定。

点击“连接监控”后，桌面先 GET `/api/v1/doctor` 核对服务角色、机器人编号和来源，再订阅实时数据。收到实时帧后才显示“上位机已连接”。若后台尚未收到机器人预览，界面提示检查采集端与隧道，可直接重试。机器人网线状态与中央上传状态分别显示。

关闭或断开桌面只结束本窗口的读取；电脑保持开机且独立后台继续运行时，relay 缓存和上传继续。

## 临时：通过 SSH 直读采集端

仅排查采集端时选择“机器人采集端临时SSH直读”，输入 `用户名@机器人IP`、已有采集端监听端口（默认 `8891`），可选系统密钥文件。首次主机指纹需通过系统终端确认，认证使用已有密钥或 `ssh-agent`。桌面不存储 SSH 密码，不安装或启停机器人程序。

该方式创建本窗口专属隧道，只读采集端，不承担中央上传；关闭窗口会关闭这条临时隧道。正常持续采集请使用后台 relay。

## 状态与边界

- 模拟来源显著标注“模拟数据 · 非实机”；ROS 2 来源仍标注“实机待验收”。接通数据不等于完成整机健康验收。
- 预检角色错误、实时机器人编号或来源变化时停止读取，避免串台。断开后清空当前健康数值与上传状态。
- 使用已活动的 relay 或临时隧道执行只读诊断，不因编辑地址框而将当前机器人的诊断请求发往另一地址。
- relay 提供往返测量的时钟偏差时，界面明确提示估计值及“硬件采样时钟仍待核对”；本机接收新鲜度独立判定。
- 温度、故障、BMS 与关节值按实际发布能力显示；缺失和过期数据保持未知。

开发验证：`tests/test_desktop_connection.py` 覆盖输入校验、只读预检、角色与身份核对、重连、迟到响应隔离、临时隧道端口和诊断地址，以及时钟偏差下的新鲜度。`tests/test_app_shell.py` 覆盖原有桌面状态和关闭行为。上述软件测试不代替真机联调。

## 本轮真机接入与最小改动范围

机器人新增文件、每核CPU更新范围及停止方式详见 [机器人侧改动清单](ROBOT_CHANGES.md)。

实际软件入口与模拟入口分开：真机中央网页使用 `http://127.0.0.1:18970/`，本机后台relay使用 `http://127.0.0.1:18972/`，SSH隧道本机端口18971转发机器人回环8891。原18940模拟环境保留。真机网页需要私有只读凭据；凭据文件位于本机 `runtime/real-robopi2/credentials/`，不写入源码或聊天，不放进机器人。

本轮机器人侧仅在用户家目录 `.local/share/rp1-monitor/20261025-r1/` 新增独立环境：Python-only采集包、离线依赖及隔离`.venv`、非秘密`profile.json`、`manifest.json`、`deployment.json`、`state/`缓存、运行日志和身份校验停止工具。不修改现有运控工作空间、策略、驱动、系统Python包、系统时钟、网卡或已有服务；没有配置开机自启。采集进程nice=10，只订阅ROS、读取现有BMS日志和Linux内核接口。停止工具只对部署记录中的PID、启动时间与本项目解释器均匹配的进程发送退出请求，保留缓存，不影响原有程序。

后续按用户要求排除CPU0：本项目采集线程及其日志读取子进程当前仅允许CPU1、2、3、7，保留本次策略运行期间已有的集合；独立`start_observer.sh`在解释器启动前应用`taskset`并拒绝重复监听。该设置不改变原运控及系统服务，也不意味着CPU0的整体使用率为零。后续手动启动请使用上述目录中的`start_observer.sh`，不要直接沿用未限制CPU或扩大CPU集合的旧启动命令。2026-10-26修复了监听自身的IMU数组兼容问题，具体文件与备份见[机器人侧改动清单](ROBOT_CHANGES.md#2026-10-26推理运行后关节读取修复)。

复用顺序：电池优先读取已运行的`bms.service`日志；关节、策略目标和IMU订阅现有ROS话题；CPU/内存/热区/uptime读取`/proc`和`/sys`。已有稳定且版本匹配的rp-server可选用现有`--rp-server-url` GET适配器，替代BMS日志来源，不启动或修复rp-server，不使用带控制能力的WS/UDP。GET状态是缓存快照，不能假定各字段具有独立采样时间，也不能据空故障列表判定整机正常。

机器人和中央时钟未同步时，新版collector提供原始窗口对应的单调锚定时间，relay记录HTTP往返上界与接收时刻。中央只对身份一致、年龄界限有效的单窗口实时传输采用此证据。原始window、ROS header、日志时间与SHA256保持不变；独立证据仅保存到latest投影。页面继续显示跨机时间未同步，历史曲线保留机器人原始时间，不能据此作跨机器硬件时间对齐。证据超时后不能回退UTC路径复活旧读数。

本轮真实链路已读取电池电量/电压/有符号电流、主机负载/热区/开机时长和配置名单内BMS进程。24关节档案保留，实际未收到的ROS反馈、温度/故障和跟踪RMS显示未知。实际控制周期对照、动作工况和长期稳定性尚未验收，不能把进程低优先级或短时CPU/RSS测量当作“对策略零影响”的保证。

本机实际读数、截图、机器人改动清单与验证记录只保存在被忽略的 `runtime/real-robopi2/`，不提交真实采集数据。代码审查见 runtime审查（本机历史材料，不随源码发布） 和 网页审查（本机历史材料，不随源码发布）。

现场补充：当前机器人关节尚未使能，因此暂无关节反馈符合现场说明。监控不发送使能指令；仅凭没有反馈不能自动判定“未使能”或故障。等现场按既有流程运行后，再观察实际话题、关节名称和数值。
