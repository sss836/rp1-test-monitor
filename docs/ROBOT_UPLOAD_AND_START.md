# RP1 监听程序：一步一步上传和启动

更新日期：2026-10-26。适用于已安装好监听环境的当前机器人 `robo@192.168.137.250`。

**TUI接入后的现行操作以[部署与通信手册](DEPLOY_AFTER_ROBOPI_TUI.md)为准。** 本文保留IMU修复阶段教程；下方旧`20261026-imu1`源码包不含TUI接入，不要按旧包更新步骤覆盖当前安装。当前已同步文件见[真机同步记录](ROBOPI_TUI_SYNC.md)。

## 先分清“上传”和“启动”

**上传**：把电脑上的新程序文件复制到机器人。只复制文件，程序不会自动运行。

**启动**：让机器人上已经装好的监听程序开始工作。

当前这台机器人已完成安装。**平时只看第一部分；更换程序版本时，再看第二部分。** 不用每次使用都重新上传。

本手册只操作本项目监听，不负责使能电机、启动策略或停止运控。

## 命令到底在哪台机器上执行

- **上位机终端**：在电脑上打开的命令窗口，命令在电脑上执行。
- **机器人终端**：用`ssh`登录后，同一个窗口开始操作机器人。

登录后，提示符可能出现`robo@robopi2`，表示正在操作机器人。这只是提示符示例，不要把提示符一起复制进命令。

上传时要另开一个上位机终端。电脑路径`/home/shn/Desktop/rp1-app`不能直接当作机器人路径使用。

# 第一部分：平时怎样启动

## 第1步：登录机器人

**在哪里执行：上位机终端。**

```bash
ssh robo@192.168.137.250
```

这条命令的含义：

- `ssh`：通过网线网络远程登录。
- `robo`：机器人上的登录用户名。
- `192.168.137.250`：当前机器人的IP地址。

按提示认证。输入密码时通常不显示字符或星号，这是正常现象；手册不保存密码。首次连接按既有SSH流程核对指纹，指纹不匹配时先核对，不关闭检查。

**成功表现**：出现机器人的命令提示符，可以继续输入命令。

后面的第2至第5步，都在这个已经登录机器人的窗口操作。

## 第2步：进入监听目录

**在哪里执行：机器人终端。**

```bash
cd /home/robo/.local/share/rp1-monitor/20261025-r1
```

`cd`的意思是“进入这个文件夹”。它只是选工作目录，还没有启动程序。

这是专门放本项目监听的目录，不是原有的`roboparty_deploy`运控目录。

**成功表现**：通常没有输出，也没有“目录不存在”之类的错误。

## 第3步：先检查它是否已经运行

**在哪里执行：机器人终端。**

```bash
curl -fsS http://127.0.0.1:8891/api/v1/state | python3 -m json.tool
```

可以理解为：**让机器人问自己，“监听程序现在是什么状态？”**

| 部分 | 含义 |
| --- | --- |
| `curl` | 向监听程序请求状态 |
| `-fsS` | 隐藏下载进度，连接或服务出错时显示错误 |
| `127.0.0.1` | 当前正在操作的机器；这里指机器人自己 |
| `8891` | 监听程序提供本地数据的端口 |
| `/api/v1/state` | 获取当前状态的接口 |
| `\| python3 -m json.tool` | 把返回内容排整齐，方便阅读 |

返回内容较长，先找这几项：

- `robot_id`应为`RP1-ROBOPI2`。
- `source_kind`应为`ros2`。
- `upload`里的`stage`应为`robot_buffer`。
- `upload`里的`collector_error`应为空字符串`""`。

**这些项目正确时，监听已经在运行。跳过第4步，直接看第6步。** 不再启动第二份。

提示无法连接时，按第4步启动。返回其他机器人身份或显示采集错误时，先核对，不通过重启运控解决。

关节暂时没有反馈、电机温度未知，不一定表示监听没有启动；这些还取决于原程序是否提供数据。

## 第4步：启动监听，让它在后台运行

**在哪里执行：机器人终端。仅在第3步确认本项目监听没有运行时执行。**

先确保仍在正确目录：

```bash
cd /home/robo/.local/share/rp1-monitor/20261025-r1
```

再执行下面**这一整行**：

```bash
nohup env -u PYTHONPATH bash ./start_observer.sh >> collector.log 2>&1 < /dev/null &
```

真正启动程序的核心是`bash ./start_observer.sh`。其余部分处理旧路径、后台运行和日志：

| 部分 | 你需要理解的意思 |
| --- | --- |
| `bash ./start_observer.sh` | 执行这个目录里的监听启动脚本 |
| `env -u PYTHONPATH` | 本次启动先去掉继承的Python查找路径，避免误运行旧源码；脚本随后加载ROS所需路径 |
| `nohup` | 忽略终端挂断信号，用于关闭SSH终端后继续运行 |
| `>> collector.log` | 普通输出追加到日志文件，不覆盖旧日志 |
| `2>&1` | 错误输出也写入同一个日志 |
| `< /dev/null` | 程序不等待这个终端的键盘输入 |
| 最后的`&` | 放到后台，终端可以继续输入命令 |

脚本会自动加载已核对的ROS环境、限制监听线程只使用**CPU1、2、3、7**，并以`nice=10`启动监听。该列表保留了本次策略运行期间已有的限制，不使用CPU0。无需再手填这些底层参数。

**成功表现**：终端通常返回后台任务编号。但这只表示命令已提交，是否真正启动还要看第5步。

后台运行不等于开机自启。目前机器人重启后，仍需重新启动监听。

## 第5步：确认这次启动成功

**在哪里执行：机器人终端。**

先看最近20行日志：

```bash
tail -n 20 collector.log
```

- `tail`：看文件末尾。
- `-n 20`：只看最后20行。
- `collector.log`：刚才保存启动输出的文件。

若出现“监听仍在运行”“启动器已在运行”或“8891端口已占用”，不要反复启动，先回到第3步核对原服务身份。

然后**再执行一次第3步的状态查询**。收到正确的机器人身份和状态，且没有`collector_error`，才算监听启动成功。

刚发出启动命令时，程序可能还在初始化。第一次查询连接失败时，等几秒再查；持续失败就查看日志，不反复提交启动命令。

需要单独核对CPU限制时，执行：

```bash
taskset --all-tasks --pid --cpu-list "$(cat collector.pid)"
```

这是一条查看命令：从`collector.pid`取出监听进程编号，再显示全部监听线程允许使用哪些CPU。当前结果都应为`1-3,7`，不含`0`。其他程序和内核中断仍可能使用CPU0，所以整机CPU0的负载不一定为零。

## 第6步：在电脑上看网页

**在哪里操作：上位机浏览器。**

打开：

```text
http://127.0.0.1:18970/robots/RP1-ROBOPI2/overview
```

此处浏览器地址中的`127.0.0.1`指电脑，因为浏览器运行在电脑上。它与第3步在机器人终端里使用的`127.0.0.1`不是同一台机器。

按原方式登录或使用私有只读凭据，选择`RP1-ROBOPI2`。不要把凭据写进地址栏。

数据经过：

```text
机器人监听 → 网线SSH隧道 → 上位机转发程序relay → 中央服务 → 网页
```

上位机原有隧道、relay和中央服务都要保持运行。机器人状态正常、网页却没更新时，按[运维参考第5节](ROBOT_UPLOAD_AND_START_REFERENCE.md#5-上位机接收并显示数据)检查这条链路，不立即重装机器人程序。

## 不用了，怎样停止监听

在机器人终端执行：

```bash
python3 /home/robo/.local/share/rp1-monitor/20261025-r1/stop_observer.py
```

这表示“请本次监听退出”。工具会核对进程身份，保留缓存，不停止策略、驱动或BMS。

命令发出后，要等监听真正退出。准备更新代码时，还需按第二部分确认端口和原进程均已释放。

# 第二部分：只有更换版本时才上传更新

**只想使用现有监听，就不执行这一部分。** 当前源码包适用于已安装好依赖的这台机器人，不是新机器人的一键安装包。

顺序是：

```text
上传 → 核对文件 → 解压 → 停止旧监听 → 备份 → 换新代码 → 检查 → 启动
```

## 更新第1步：在电脑上找到上传文件

**在哪里执行：另开一个上位机终端。不要在SSH登录机器人的窗口执行。**

```bash
cd /home/shn/Desktop/rp1-app
sha256sum runtime/rp1-monitor-agent-source-20261026-imu1.tar.gz
```

- `cd`：进入电脑上的工程目录。
- `.tar.gz`：装着监听Python代码的压缩包。
- `sha256sum`：计算文件的64位十六进制校验值，可理解为文件“指纹”。保留结果，稍后比较。

该包是2026-10-26整理的快照，包含每核CPU采集功能和真实ROS IMU数组兼容修复。旧的`20261025-cpu1`包包含已发现的IMU读取缺陷，不再用于覆盖当前安装。之后代码有变化时需要新包和新名称。

## 更新第2步：把包复制到机器人

**在哪里执行：刚才的上位机终端。**

```bash
scp runtime/rp1-monitor-agent-source-20261026-imu1.tar.gz robo@192.168.137.250:~/
```

- `scp`：通过SSH复制文件。
- 前面的路径：电脑上的文件。
- `robo@192.168.137.250`：接收文件的机器人和用户名。
- `:~/`：放进机器人用户家目录，也就是`/home/robo/`。

**成功表现**：复制完成，命令返回，没有报错。此时只是上传完成，机器人仍使用原来安装的代码。

## 更新第3步：确认收到的是同一个包

**在哪里执行：机器人终端。未登录时先执行第一部分第1步。**

```bash
sha256sum ~/rp1-monitor-agent-source-20261026-imu1.tar.gz
```

将输出的前64个字符，与电脑“更新第1步”的结果比较。**必须完整一致**才继续，不能只看前几位或文件名。

一致说明收到的是电脑上那份已知包，不代表任意来源的包都可信。

## 更新第4步：解压到新文件夹

**在哪里执行：机器人终端。后续更新保持在同一个终端完成。**

```bash
cd /home/robo/.local/share/rp1-monitor/20261025-r1
mkdir -p releases
release="$(mktemp -d "$PWD/releases/source-XXXXXXXX")"
tar -xzf ~/rp1-monitor-agent-source-20261026-imu1.tar.gz -C "$release"
```

逐行含义：

1. `cd ...`：进入本项目监听目录。
2. `mkdir -p releases`：准备放新版本的文件夹，已存在也可使用。
3. `mktemp -d ...`：创建一个全新的子目录，避免覆盖旧版本。末尾`X`由工具换成随机字符，不必手填。
4. `release=...`：把新目录位置暂时记在名字`release`里，后面的`$release`就代表这个位置。
5. `tar -xzf ... -C ...`：解压源码包，放进这个新目录。

**成功表现**：没有解压错误。此时还未替换原代码，旧监听可以继续运行。

接下来会用到三个临时名字：`release`是新源码位置，`package_dir`是实际安装位置，`backup`是旧代码备份位置。它们只在当前终端保留，中途换终端会丢失。

## 更新第5步：停止旧监听，等它退出

**在哪里执行：同一个机器人终端。**

```bash
python3 ./stop_observer.py
```

它只请求本项目旧监听退出。先停再换代码，是为了避免程序运行时混用新旧文件。

查看端口：

```bash
ss -ltn '( sport = :8891 )'
```

意思是“查看8891端口是否还有程序等待连接”。只有表头、没有`LISTEN`记录，表示端口已释放。

再查看旧进程：

```bash
ps -p "$(cat collector.pid)" -o pid=,stat=,args=
```

`cat collector.pid`读取旧监听的进程编号，`ps`查看这个进程。**不再显示旧监听进程行时，才继续。** 若仍显示，等待后重新检查。

停止工具报告身份不匹配时，先核对记录。不要用`killall python`或停止运控来清出端口。

## 更新第6步：先备份，再换代码

**在哪里执行：同一个机器人终端，仍在本项目监听目录中。**

确定安装位置并检查文件：

```bash
package_dir="$PWD/.venv/lib/python3.12/site-packages/rp1_monitor"
ls "$package_dir/__main__.py" "$release/rp1_monitor/__main__.py"
```

- `package_dir=...`：记住真正安装程序的位置。
- `ls`：列出旧程序和新程序的入口文件。应看到两条文件路径，且没有“文件不存在”的错误。

若检查失败或目录不存在，不继续复制。这说明当前机器不能直接套用这个安装路径。

备份旧代码：

```bash
mkdir -p backups
backup="$(mktemp -d "$PWD/backups/code-XXXXXXXX")"
cp -a "$package_dir" "$backup/rp1_monitor"
```

先准备`backups`文件夹，再建立独立备份目录，最后用`cp -a`复制整份旧监听代码并保留文件属性。**备份不会换新代码，是给更新失败保留退路。**

检查和备份都成功后，再替换：

```bash
cp "$release/rp1_monitor/"*.py "$package_dir/"
```

意思是“把新包里的Python文件复制到实际安装位置”。`*.py`只选Python代码，本次包有46个Python文件。

只覆盖隔离环境内本项目代码，不覆盖依赖、`profile.json`、缓存、启动/停止工具或`roboparty_deploy`。

## 更新第7步：检查是否加载了正确代码

**在哪里执行：同一个机器人终端。**

先看Python从哪里找到监听：

```bash
env -u PYTHONPATH .venv/bin/python -B -c 'import rp1_monitor; print(rp1_monitor.__file__)'
```

它不会启动监听，只显示代码路径。结果应是：

```text
/home/robo/.local/share/rp1-monitor/20261025-r1/.venv/lib/python3.12/site-packages/rp1_monitor/__init__.py
```

如果显示`releases`里的其他源码、家目录里的旧代码或其他位置，先停止，不启动。

再检查模块能否加载：

```bash
env -u PYTHONPATH .venv/bin/python -B -c 'from rp1_monitor.agent import AgentSettings; from rp1_monitor.host_cpu import CPUObserver; print("导入通过")'
```

`import`可理解为“请Python加载代码，看看有没有缺文件、依赖或语法错误”。它不使能关节，也不启动策略。

**成功表现**：显示“导入通过”，没有报错。

## 更新第8步：启动并验证

仍在机器人监听目录中，执行第一部分第4步的后台启动命令。再按第一部分第5步检查日志和状态，回电脑看网页。

到这里才完成“上传新文件并让它生效”。仅上传或解压不会自动让新代码生效。

若导入失败，保持监听停止，在同一个终端用刚才备份恢复：

```bash
cp "$backup/rp1_monitor/"*.py "$package_dir/"
```

它只恢复本项目Python代码。之后重新执行更新第7步的检查。终端已关闭时，先核对本次备份目录，不能用空变量或随意选的旧目录恢复。

## 需要排查时再看

- **新机器人首次安装**：包不含ROS、隔离依赖、设备档案或启动工具，需先准备环境。
- **ROS话题没数据**：启动器继承终端的`ROS_DOMAIN_ID`，未设置时默认为0；应与原运控消息分组一致。不要修改正在运行的原运控来尝试连通监控。
- **缓存**：机器人暂存每秒摘要，上位机确认接收后释放记录。128MiB是待传载荷预算，满时可能淘汰最早未传摘要；剩余空间低于512MiB时摘要落盘线程停止。不要为启动监听删除缓存或录包。
- **更细的排查命令**：查看[运维参考](ROBOT_UPLOAD_AND_START_REFERENCE.md)。
- **机器人侧改动范围**：查看[改动清单](ROBOT_CHANGES.md)。
