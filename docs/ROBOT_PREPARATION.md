# 没有实机时，先准备什么

现在可以先完成采集包、配置模板、上位机模拟验证和现场检查材料。机器人环境版本、网线地址、SSH账号、进程名单及物理映射需要拿到机器后确认，不凭空填写。

## 三个位置分别做什么

| 位置 | 需要准备 | 配置由谁持有 |
|---|---|---|
| RP1机器人 | 一份只读采集程序、匹配ROS的Python环境、设备编号、专用磁盘缓存目录 | ROS/工作空间路径、机器人档案；不配置中央地址或中央上传令牌 |
| 上位机电脑 | SSH隧道、独立后台relay、Qt界面 | 中央地址、该设备的上传凭据、电脑缓存目录 |
| 中央服务器 | 监控API、数据库、网页、诊断Agent及可选模型配置 | 设备登记、页面认证、模型服务配置 |

机器人无需Wi-Fi或外网。安装依赖可以在匹配机器人CPU架构、Python和ROS版本的环境中提前下载，现场离线安装。模型调用不发生在机器人上。

## 机器人侧的最小接入顺序

### 第一步：由现场人员确认实际环境

拿到机器后，把 `scripts/check_robot_readiness.py` 复制过去，在现有ROS环境下用计划运行采集程序的Python执行：

```bash
python3 -B check_robot_readiness.py
# 需要机器可读结果时，输出到终端：
python3 -B check_robot_readiness.py --json
```

检查脚本仅使用Python标准库，读取系统版本、架构、当前ROS发行版、依赖可导入性及磁盘空间。它不安装依赖、不修改网卡、不连接网络、不启动ROS节点、不启停任何服务、不读取进程参数、环境变量全集或BMS原始日志。不会创建缓存目录或测试文件。

若当前终端尚未加载ROS，检查结果会标为待核对；现场人员应使用实际ROS与工作空间路径加载环境后再运行。`rclpy`与采集Python的ABI必须匹配。项目要求Python 3.10+，若机器人版本较旧，应先确定适配方案，不直接升级机器人系统或复制电脑虚拟环境。

`imports_ready`仅代表基础导入通过；实际Topic、权限、SSH、物理映射和运行开销仍未验证。在普通电脑执行得到的是电脑环境，不能写成RP1检查通过。

### 第二步：安装采集包和匹配依赖

机器人只需本工程的 `agent` 依赖，不需要桌面GUI、数据库服务器或模型服务。ROS包由现场既有ROS安装提供；安装前需确认 `rclpy`、`sensor_msgs`、`diagnostic_msgs` 能在相同Python中导入。

可用 `python3 -m venv --system-site-packages .venv-agent` 创建匹配环境。实际路径、安装权限和离线依赖包由现场人员确认；不能把上位机的 `.venv` 直接复制到机器人。详细方法见 [ROS接入说明](ROS_CONNECT.md)。

### 第三步：填写少量配置

从 [agent.env.example](../deploy/agent.env.example) 开始，核对：

- 机器人唯一编号，例如 `RP1-001`。
- 实际ROS与运控工作空间的 `setup.bash` 路径。
- 能导入ROS包的采集Python路径。
- 一个有写权限、容量明确的专用缓存目录。
- 与现有运控一致的ROS Domain及RMW/DDS环境。
- 如需电机温度/故障监控，提供经核对的设备档案：关节名、总线、电机ID和协议。

`Humble`、`/home/robot/ros_ws` 等模板值只是示例。机器人不需要中央IP、上传Token或模型Key。

### 第四步：先前台运行并核对数据

在已加载正确ROS环境的终端中，使用实际Python、设备编号和已准备的目录：

```bash
.venv-agent/bin/python -m rp1_monitor agent --source ros2 \
  --robot-id RP1-001 --state-dir /实际专用缓存目录 --port 8891
```

如已有经核对的档案，再加 `--profile /实际档案路径/profile.json`。采集程序只监听机器人本机回环地址，电脑通过独立SSH隧道访问。首次不必配置开机自启；数据核对、资源开销和断线恢复通过后，再审阅 [systemd模板](../deploy/rp1-monitor-agent.service)。

## 哪些监控可以先做，哪些需要运控人员配合

| 数据 | 现有入口 | 现场需确认 |
|---|---|---|
| 主机CPU、内存、热区温度 | 机器人本机 `/proc`、`/sys` | 内核热区是否提供、读权限及实际运行开销 |
| 关节反馈、策略目标、IMU | 订阅已有ROS Topic | 类型、QoS、名称、单位和时间体系 |
| 电池数据 | 跟随既有BMS日志，或仅GET已运行的匹配rp-server | 读取权限、字段来源和新鲜度；不为监控另启硬件服务 |
| 电机温度、MOS温度和故障码 | 运控已有诊断发布；缺少时需评估本项目补丁 | 版本基线、构建依赖、实际总线/ID/关节映射 |
| 各核心进程CPU、RSS、线程数、重启变化 | 已有只读 `/proc` 采集与模拟验证，[配置说明](PROCESS_MONITOR.md) | 现场提供实际唯一 comm，核对权限、命名空间与开销 |

电机诊断发布是额外配合项，不能直接套补丁。先由运控维护者核对 [补丁基线及检查方式](../integrations/robot-health/README.md)，在源码副本构建验证后，再走原团队的部署流程。基础监测可先接入，缺少的指标明确显示未提供。

## 以后交给现场人员的信息清单

1. 只读环境检查结果：系统、CPU架构、Python、ROS及依赖状态。
2. 可用的SSH用户名与网线IP、既有ROS/工作空间路径；不发送密码或私钥。
3. 实际Topic及类型/QoS、BMS来源、运控/驱动版本和物理映射。
4. 希望关注的核心进程或systemd服务名，以及已批准的缓存目录与容量。

有这些信息后，才能生成该台机器准确的配置和离线依赖清单。目前没有连接实机，准备脚本与模拟验证不代表实机验收。完整电脑relay连接步骤见 [网线上位机说明](WIRED_RELAY.md)。
