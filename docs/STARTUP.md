# 机器人端安装与启动：每一步在做什么

本教程属于 [sss836/rp1-test-monitor](https://github.com/sss836/rp1-test-monitor)，只部署机器人端 `rp1-monitor-robot`。电脑上位机、网页、长期保存和 AI 的教程在 [sss836/rp1-monitor-app](https://github.com/sss836/rp1-monitor-app#readme)。

## 1. 先分清运行位置

```text
机器人：已有 ROS/BMS → 只读监听 127.0.0.1:8891
                              │ 网线上的 SSH 转发
电脑：                      后台 relay → PostgreSQL → 上位机/网页
                                                   → 可选 AI API
```

机器人端不直接上传中央、不配置中央地址或凭据，不运行 AI。TUI 菜单不用一直打开；本项目只在上位机人工选择检查时调用已安装 TUI 的被动插件。安装或启动监听不会自动运行整套自检。

原运控、驱动与 BMS 按原有操作流程运行；监听不会替你启动、停止、使能或修复它们。没有关节发布者时，仍可观察已提供的主机/BMS 数据，关节项显示缺失。

## 2. 登录后，核对安装条件

从电脑通过网线登录机器人。下面只有 SSH 地址是当前连接形式示例，使用现场确认的地址，密码在 SSH 提示时输入：

```bash
ssh robo@192.168.137.250
```

提示符变为机器人用户后，后续安装和启动命令就在机器人执行。使用普通用户，不在命令前加 `sudo`。

| 必须确认的内容 | 含义 |
| --- | --- |
| 已有 ROS 及其 `setup.bash` | 复用机器人现有环境，不安装另一套 ROS |
| Python 与 ROS 的 ABI 一致 | 例如 Jazzy 常用 Python 3.12；以现场安装为准，本项目要求 Python 3.10+ |
| `rclpy`、`sensor_msgs`、`diagnostic_msgs` 可用 | 由现有 ROS 提供，不用 pip 另装 ROS |
| 原运控的 ROS Domain/RMW/DDS 配置 | 订阅者和发布者必须能互相发现；不要擅自改为 Domain 0 或替换配置 |
| CPU1、2、3、7 可用于监控 | 当前启动器固定使用这些核，排除 CPU0；换硬件须先审阅适配 |
| 唯一机器人编号 | 用于数据身份与电脑绑定，不能几台机器人共用同一编号 |
| 普通用户的读取权限 | BMS 日志和部分系统信息可能受限；权限不足时保留缺失，不以 root 运行整个监听 |

可以只读查看架构、Python 和 CPU 编号：

```bash
uname -m
python3 --version
lscpu -e=CPU,ONLINE
```

这些命令只显示信息，不配置硬件。ARM64 通常显示 `aarch64`；结果不匹配时先确认适配，不从电脑复制虚拟环境。

## 3. 获取机器人专用源码

机器人在维护时可以访问 GitHub，且已安装 Git 时：

```bash
git clone https://github.com/sss836/rp1-test-monitor.git
cd rp1-test-monitor
```

第一条创建新的源码目录，第二条进入它；此时还没有安装或启动监听。已有同名目录时先检查其内容，不删除或覆盖，也不直接拉取后替换正在使用的安装。

机器人不需要为了日常监控接外网。离线现场可以在电脑下载本仓库源码，通过已批准的传输方式放到机器人的独立新目录，再进入该目录继续。只传机器人仓库，**不传电脑仓库、电脑 `.venv`、电脑 `runtime` 或数据库文件**。

## 4. 在同一个终端准备已有 ROS/DDS 环境

以已有 Jazzy 为例，实际不是这个路径时换成现场路径：

```bash
export RP1_ROS_SETUP=/opt/ros/jazzy/setup.bash
source "$RP1_ROS_SETUP"
export RP1_ROBOT_ID=RP1-NEW-01
```

- `RP1_ROS_SETUP` 告诉安装器以后从哪里加载现有 ROS。
- `source` 只在当前终端加载环境，不修改原 ROS 文件。
- `RP1_ROBOT_ID` 是这台机器的唯一监控编号；把示例 `RP1-NEW-01` 换为实际值，并在电脑端使用相同编号。

在这个终端保留或按运控维护者提供的取值设置 `ROS_DOMAIN_ID`、`RMW_IMPLEMENTATION`、`RMW_FASTRTPS_USE_QOS_FROM_XML`、`FASTRTPS_DEFAULT_PROFILES_FILE`。不要为了接监控改原运控配置，也不要照抄其他机器的 DDS 文件。

安装器把这几个环境变量的当前取值写入自己的 `observer-config.json`。若它们未设置，不会替你推断真实值。以后启动器会加载指定 ROS setup 并恢复已记录的非空取值；在不同终端启动仍应避免继承冲突的 ROS 环境。自定义运控工作空间若还需要额外环境，先由维护者核对启动需要，默认安装器不会自动寻找或 source 任意工作空间。

## 5. 安装到独立新目录

### 可以使用包源时

在源码根目录运行：

```bash
bash scripts/install-robot.sh
```

脚本创建本项目独立 Python 环境，安装机器人专用包及其依赖，然后生成待核对档案和启动器；**不会启动监听**。普通用户安装，脚本明确拒绝 root，不安装或升级系统包、ROS 和 TUI。

### 机器人无外网时

由维护者先在匹配目标 ARM64、Python 版本和系统的准备环境中，准备 `rp1-monitor-robot==0.4.0` 及其全部依赖 wheel。目录中还应准备 `pip` 的 `py3-none-any.whl`，避免依赖机器人系统是否提供 pip/ensurepip。二进制依赖必须匹配目标架构和 Python ABI；项目自身的纯 Python wheel 不代表其他依赖也能跨架构使用。

把这些 wheel 放入机器人本地目录，例如 `~/rp1-robot-wheels`，再执行：

```bash
export RP1_WHEELHOUSE="$HOME/rp1-robot-wheels"
bash scripts/install-robot.sh
```

`RP1_WHEELHOUSE` 指定本地依赖目录；安装器使用 `--no-index`，不访问包源，缺少依赖就报错。目录必须包含机器人专用 wheel，旧统一 `rp1-monitor` wheel 或电脑包 `rp1-monitor-pc` 不能代替。

### 安装究竟改哪里

默认只在普通用户自己的新目录写入：

```text
~/.local/share/rp1-monitor/github/
├── .venv/                 # 机器人专用 Python 包与依赖，复用已有系统 ROS
├── .tmp/                  # 本项目安装临时文件
├── .pip-cache/            # 本项目安装缓存
├── observer-config.json   # ID、ROS/DDS、可选 TUI 执行器路径
├── profile.json           # 待核对的设备档案
└── start-observer.sh      # 手动启动器
```

已有目标目录时安装器**拒绝覆盖**。安装失败可能留下这个新目录用于检查；不要反复重试或删除现场旧目录来“修复”。需要新安装目录时可由维护者明确设置 `RP1_MONITOR_INSTALL_DIR`，后续应使用实际输出的新路径，不能继续照抄默认启动命令。

`observer-config.json` 不含 SSH 密码、数据库连接、上传令牌或模型 Key。安装器不更改 `robot.yaml`、策略、权重、驱动、CAN 参数、原 BMS 服务或 systemd；没有开机自启。

`profile.json` 初始是未知档案，不是自动探测结果。只填写核对过的版本、BMS 来源、进程 `comm` 和电机映射；未确认的映射留空，`physical_mapping_verified` 保持 `false`。不要将模拟映射当作真机映射。电脑上的 24/28 自由度展示也需要按真实配置登记。

## 6. 手动前台启动

确认没有另一份本项目监听后运行：

```bash
bash "$HOME/.local/share/rp1-monitor/github/start-observer.sh"
```

启动器先限制到 CPU1、2、3、7，再初始化 Python/ROS；子线程和自有子进程继承此 CPU 集合，不能运行在 CPU0。`nice -n 10` 降低调度优先级，**不限制 CPU 百分比**，不是零开销承诺。已有父进程优先级可能影响最终 nice 值。

启动器还会检查同一目录的锁和 `127.0.0.1:8891` 端口。已有实例或端口占用就拒绝启动，不会自动结束原进程。出现冲突时先核对身份，不批量杀 Python 进程。

保持这个终端打开，日志显示在终端中；按 **`Ctrl+C`** 只请求本次监听退出，运控、推理和 BMS 不随之停止。机器人重启后，重新登录并运行这条命令；本教程不安装后台托管或自动重启。

运行后会在自己的 `state/` 目录保存待交给电脑的摘要和自检报告等本地状态。默认 `--cache-mib 128 --reserve-mib 512` 是摘要缓存预算和磁盘预留参数，**不是进程内存上限，也不是整个目录的大小上限**。这份有限缓存不能代替长期记录；长期选择指标、保存频率和测试曲线由电脑端 PostgreSQL 链路负责。

## 7. 在电脑连接，不在网页里部署机器人

机器人监听启动后，转到电脑，按 [rp1-monitor-app 的开启教程](https://github.com/sss836/rp1-monitor-app#readme)启动上位机。设备连接里填写 SSH 地址，例如 `ssh robo@192.168.137.250`，密码在本机界面交互输入，核对主机指纹后连接。

电脑后台负责建立 SSH 转发、绑定真实机器人编号、接收缓存和上传数据库。机器人接口只绑定本机 `127.0.0.1:8891`，不需要为监控开放公网端口、配置 Wi-Fi 或中央凭据。网页负责显示测试数据、曲线和报告；AI Key 也只在电脑端配置。

## 8. 怎样判断接通了什么

| 界面现象 | 能说明什么 |
| --- | --- |
| 机器人身份匹配、来源为 `ros2`、时间持续更新 | 采集链路正在提供真实来源的观测，不等于整机验收通过 |
| CPU、内存、主控热区在更新 | 主机采集可用；主控板温度不是电机温度 |
| SOC、电池电压、电流在更新 | 对应已有 BMS 数据可读；未提供的电池温度仍保持未知 |
| 关节位置、力矩等显示缺失 | 先核对发布者、ROS Domain/DDS、类型/QoS 和读取错误；不能仅凭缺失判机器人故障 |
| 电机温度、MOS 温度或关节电压缺失 | 原发布者未提供、数据无效或映射未确认时保持未知；不会为补齐字段发送总线读取命令 |
| 电脑显示已确认入库、历史曲线可查询 | 对应记录已进入电脑长期库；仅连接成功不能证明全部指标已经保存 |

本仓库不发布 `/joy`、`/cmd_vel`、`/action`，不调用电机、标零或推理启停服务。只读也有 CPU、内存和磁盘开销，长期站立/跑步前需要单独核对实际资源和控制周期，不能用软件模拟结果代替实机验证。

## 9. 已经有旧监听的现场，不自动切换

当前现场旧安装路径为：

```text
/home/robo/.local/share/rp1-monitor/20261027-recordings/start-observer.sh
```

这份旧安装使用以前的统一包，本仓库不会自动更新、停止或替换它。已有正确旧监听时继续使用原启动器，**不要同时启动新包**。后续切换需要先审阅新旧文件、安装目录、设备档案和启动参数的差异，再只停止旧监听，在独立目录安装验证；本教程不执行这次切换，也不修改原运控。

TUI 已安装只表示被动自检入口可能可用，不证明版本、插件依赖或全部项目已验收。启动器仅查找已安装执行器；多版本冲突时拒绝自动选择，由维护者核对 `observer-config.json` 中的 `tui_executor` 绝对路径。TUI 检查由上位机人工单项触发，不会在监听启动或查看报告时自动跑全部插件，不自动安装依赖或循环修复。
